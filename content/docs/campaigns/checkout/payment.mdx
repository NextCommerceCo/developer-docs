Checkout supports credit cards (tokenized with Spreedly), express wallets (PayPal, Apple Pay, Google Pay), and redirect methods such as Klarna, Affirm, and iDEAL. This page covers the card form and payment-method selection; wallet buttons are in [Express Checkout](./express-checkout).

---

## Credit Card Fields

Card number and CVV are rendered by Spreedly inside iframes, so raw card data never enters your page or server. Provide mount points by ID or field attribute:

| Field | Mount point |
|---|---|
| Card number | `data-next-checkout-field="cc-number"` (or `id="spreedly-number"`) |
| CVV | `data-next-checkout-field="cvv"` (or `id="spreedly-cvv"`) |
| Expiry month | `data-next-checkout-field="cc-month"` or `data-next-checkout-field="exp-month"` |
| Expiry year | `data-next-checkout-field="cc-year"` or `data-next-checkout-field="exp-year"` |
| Cardholder name | `data-next-checkout-field="card-name"` |

```html
<div data-next-checkout-field="cc-number"></div>
<div data-next-checkout-field="cvv"></div>
<select data-next-checkout-field="cc-month"></select>
<select data-next-checkout-field="cc-year"></select>
<input  data-next-checkout-field="card-name" type="text" />
```

Card number and CVV must be empty `<div>` containers, not `<input>`s — Spreedly mounts a secure iframe inside each. The SDK assigns the `id` Spreedly needs (`spreedly-number` / `spreedly-cvv`) automatically, so the `id="…"` form is equivalent but not something you need to write. The month and year dropdowns are populated automatically on load.

<Callout type="warn">
A Spreedly environment key must be set in your SDK configuration. Without it the credit card fields will not initialize. See [Configuration](../configuration).
</Callout>

### Tokenization

On submit, the SDK calls Spreedly to tokenize the card and receives a single-use token. Only that token — never the card number — is sent to the order API. If tokenization fails, the SDK shows the error and does not create an order.

When the iframe fields are ready the SDK emits `checkout:spreedly-ready`; on a successful token it emits `payment:tokenized`; on failure it emits `payment:error`.

### Card validation

| Field | Rule |
|---|---|
| Card number | Validated live by Spreedly |
| CVV | Validated live by Spreedly |
| Expiry month | Must be selected |
| Expiry year | Must be selected |
| Expiry combined | Card must not be expired |
| Cardholder name | Minimum 2 characters |

## Payment Method Selection

When the page offers more than one payment method, use radio inputs named `payment_method`:

```html
<label><input type="radio" name="payment_method" value="credit" checked /> Credit Card</label>
<label><input type="radio" name="payment_method" value="paypal" /> PayPal</label>
```

The SDK reads the selected method and shows or hides the matching form section. You can also mark a method element with `data-next-payment-method="<value>"` (or legacy `os-payment-method`).

### Supported values

| UI value | Sent to API as | Validation path |
|---|---|---|
| `credit` | `card_token` | Full form + card fields |
| `paypal` | `paypal` | Express radio (configurable) |
| `apple_pay` | `apple_pay` | Express radio (configurable) |
| `google_pay` | `google_pay` | Express radio (configurable) |
| `klarna` | `klarna` | Always full form |
| `affirm` | `affirm` | Always full form |
| `ideal` | `ideal` | Always full form |
| `bancontact` | `bancontact` | Always full form |
| `giropay` | `giropay` | Always full form |
| `sepa_debit` | `sepa_debit` | Always full form |
| `sofort` | `sofort` | Always full form |
| `swish` | `swish` | Always full form |
| `twint` | `twint` | Always full form |
| `link` | `link` | Always full form |

Values are case-insensitive and separators are interchangeable (`apple-pay` = `apple_pay`). A value not in this table is passed through to the orders API unchanged, so the API decides whether it can be charged.

<Callout type="warn">
SEPA Direct Debit's value is `sepa_debit` — the name the orders API uses — not `sepa_direct` as some platform guides call the same method.
</Callout>

<Callout>
The selected payment method element gets the `next-selected` class. Payment form sections animate open and closed using the `payment-method__form--expanded` / `--collapsed` classes.
</Callout>

## Validation by Payment Method

Which validation runs on submit is decided by the selected method, in this order:

1. **Express buttons** (the [Express Checkout](./express-checkout) container, including the Link button) — one click, no form validation.
2. **PayPal / Apple Pay / Google Pay radios** — controlled by `paymentConfig.expressCheckout`: with `requireValidation: false` the submit is handed straight to the express checkout processor — the same path as the buttons — and no form validation runs; with `requireValidation: true` only the fields in `requiredFields` are checked.
3. **Card** — always full form validation plus card fields.
4. **Everything else** (Klarna, Affirm, iDEAL, Bancontact, giropay, SEPA `sepa_debit`, Sofort, Swish, TWINT, and the Link radio) — always full form validation. `requireValidation` and `requiredFields` have no effect on these methods.

Link appears in both paths: as an express **button** it skips the form entirely, but as a `payment_method` **radio** it always runs full form validation, like the other redirect methods.

`requiredFields` is a single shared list — there is no per-method configuration. To require an extra field for one method only (for example, phone for Affirm), toggle `data-next-required="true"` on that input when the method is selected; the attribute is re-read at submit. See [required fields](./form#required-fields).

<Callout>
The form's validation is separate from what the payment gateway needs to authorize the payment. For example, Affirm requires a phone number in addition to the name, email, and address every redirect method submits, while Klarna does not — a missing gateway field surfaces as an error from the orders API, not as a form validation error.
</Callout>

## Payment Errors

Card and wallet errors are written into dedicated containers when present:

```html
<div data-next-component="credit-error">
  <span data-next-component="credit-error-text"></span>
</div>
```

| Container | Used for |
|---|---|
| `data-next-component="credit-error"` / `credit-error-text` | Credit card / tokenization errors |
| `data-next-component="paypal-error"` / `paypal-error-text` | PayPal errors |
| `data-next-component="express-error"` / `express-error-text` | Express wallet errors |

Every payment failure also emits a `payment:error` event with a message you can listen for.
