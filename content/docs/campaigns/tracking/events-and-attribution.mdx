## Event names by SDK version

Starter templates pin SDK 0.4.43. Use the 0.4.x column for those funnels. The table lists events emitted by 0.4.43, including events you trigger manually. The last column describes the 0.4.43 trigger unless it explicitly says otherwise.

| Moment | SDK 0.4.x event | SDK 0.5.0 event | Fires on |
| --- | --- | --- | --- |
| Page load or user context refresh | `dl_user_data` | `page_viewed` | Every page load in auto mode; also on supported context refreshes |
| Product list viewed | `dl_view_item_list` | `product_list_viewed` | A page with multiple packages, a configured view-item-list meta tag, or `next.trackViewItemList()` |
| Product viewed | `dl_view_item` | `product_viewed` | A single or selected package, a configured view-item meta tag, or `next.trackViewItem()` |
| Item added | `dl_add_to_cart` | `product_added_to_cart` | Cart item added in auto mode; 0.5.0 also reports carts filled before page load |
| Item removed | `dl_remove_from_cart` | `product_removed_from_cart` | Cart item removed in auto mode |
| Package swapped | `dl_package_swapped` | No direct equivalent | Package selector in swap mode; 0.5.0 removes this event and sends removal and addition events |
| Cart updated | `dl_cart_updated` | `cart_updated` | Cart update in auto mode |
| Checkout started | `dl_begin_checkout` | `checkout_started` | Checkout form initialization with a non-empty cart, in any mode |
| Shipping entered | `dl_add_shipping_info` | `checkout_shipping_address_submitted`, `checkout_shipping_method_submitted` | Shipping method selection, autofill or address autocomplete, in any mode |
| Payment entered | `dl_add_payment_info` | `checkout_payment_info_submitted` | Complete card fields, an express payment button press or redirect payment submission, in any mode |
| Order purchased | `dl_purchase` | `checkout_completed` | First SDK page that freshly fetches the paid order, in auto mode |
| Upsell viewed | `dl_viewed_upsell` | `upsell_viewed` | Upsell page |
| Upsell skipped | `dl_skipped_upsell` | `upsell_skipped` | Shopper skips an upsell |
| Upsell purchased | `dl_upsell_purchase` | `upsell_completed` | Next SDK page after acceptance, from the queued event |
| Scroll threshold reached | `dl_scroll_depth` | No mapping confirmed | Configured scroll-tracking meta tag thresholds, once per threshold per page, in any mode |
| Exit intent shown | `dl_exit_intent_shown` | No direct tracking event; data layer only | Exit-intent popup shown, in auto mode |
| Exit intent accepted | `dl_exit_intent_accepted` | No direct tracking event; data layer only | Exit-intent popup clicked, in auto mode |
| Exit intent dismissed | `dl_exit_intent_dismissed` | No direct tracking event; data layer only | Exit-intent popup dismissed, in auto mode |
| Exit intent closed | `dl_exit_intent_closed` | No direct tracking event; data layer only | Exit-intent popup closed, in auto mode |
| Exit intent action | `dl_exit_intent_action` | No direct tracking event; data layer only | Exit-intent action, in auto mode |
| Sign-up | `dl_sign_up` | No mapping confirmed | Your call to `next.trackSignUp(email)` |
| Login | `dl_login` | No mapping confirmed | Your call to `next.trackLogin(email)` |
| Custom event | Your event name | No mapping confirmed | Your call to `next.trackCustomEvent(name, data)` |

SDK 0.4.43 defines `dl_page_view`, `dl_route_changed`, `dl_view_cart`, `dl_select_item`, `dl_view_search_results` and `dl_subscribe`, but never emits them. The SDK Meta provider's `PageView` comes from `dl_user_data`.

The `dl_*` event stream still exists on 0.5.0 as a deprecated compatibility layer. Its shipping compatibility event is sent only for the first shipping-address or shipping-method event per checkout. Unconfirmed: the 0.5.0 mappings and behavior above were checked in source, but not in a live funnel. No 0.5.0 mapping is confirmed for scroll depth, sign-up, login or your custom event names.

## Purchase event

On SDK 0.4.43, `dl_purchase` fires on the first SDK page that does a fresh fetch of the order from `?ref_id=` or `?order_ref_id=` after payment. This can be your upsell page before the receipt. Creating the order on the checkout page does not emit it. A cached order with the same reference, loaded less than 15 minutes ago, does not emit it again.

Set `window.nextConfig.analytics.enabled` to `true` and `window.nextConfig.analytics.mode` to `'auto'` for automatic `dl_purchase`. Only `mode === 'auto'` starts the auto-trackers; omitting `mode` does not enable them.

| Field | SDK 0.4.43 value |
| --- | --- |
| `ecommerce.transaction_id` | Order number, stringified. If absent, the SDK falls back to `order.ref_id`, then `orderId`, then `transactionId`. Without an identifier it does not build the event |
| `event_id` | Same value as `ecommerce.transaction_id` |
| `ecommerce.value` | Item revenue: sum of item price multiplied by quantity. Tax and shipping are not added |
| `ecommerce.tax` | `order.total_tax` |
| `ecommerce.shipping` | Shipping on your store's displayed tax basis |
| `ecommerce.currency` | Order currency, or campaign currency if absent |
| `ecommerce.items` | Order line items |
| `ecommerce.items[].item_id` | Product SKU, falling back to `SKU-<id>` |
| `ecommerce.items[].item_variant_id` | Variant identifier, when available |

For tax-exclusive stores, `value` excludes tax and shipping. The per-unit price uses the store's displayed basis: tax-exclusive for tax-exclusive stores, tax-inclusive for VAT stores. On a VAT store, item tax is already in `value`, and `tax` is also sent separately.

An unpaid order with `payment_complete_url` does not fire `dl_purchase`. A payment-failure landing also vetoes it. The failure check uses the recorded failure path, or `?payment_failed=true` unless the current path matches the recorded success path.

The SDK deduplicates purchases in `localStorage` under `nextDataLayer_reportedPurchases`, keeping the last 20 transaction IDs without a time expiry. The key can have the SDK's scope suffix. It records an ID after the event is pushed to `window.NextDataLayer`.

In the live SDK 0.4.43 test, `transaction_id` and `event_id` were the order number. The purchase fired on the upsell page with `value: 12`, `tax: 0` and `shipping: 0`. The order total became 15 after the upsell. Revisiting the upsell page did not send another `dl_purchase`.

## Upsell event

On SDK 0.4.43, `dl_upsell_purchase` uses `transaction_id: <order reference>-US<n>`, where `n` counts accepted upsells. Its `event_id` is the same string. The reference can differ from the order number used by `dl_purchase`.

The event reports the accepted upsell line only, with `tax: 0` and `shipping: 0`, except for the bundle behavior below. It is queued in `sessionStorage` and replayed on the next SDK page where analytics initializes. If it is more than 5 minutes old at replay, it is dropped. Acceptance without navigation leaves it queued.

The value basis varies by acceptance path:

| Acceptance path | `value` basis |
| --- | --- |
| Accept-upsell button, single package | Added order line on the store's displayed tax basis |
| Accept-upsell button, bundle | One event per bundle item, each with the whole bundle total. Summing these events overcounts bundle revenue |
| Upsell page or `next.addUpsell` | Added line's `price_incl_tax`, falling back to campaign package price multiplied by quantity |
| Package toggle | Campaign package price multiplied by quantity |

No attribution is sent on upsell API calls. The added lines belong to the original order, which received attribution when it was created. The analytics event itself carries the current attribution at replay time.

## Attribution captured from the URL

On SDK 0.4.43, these URL values become fields in your order's `attribution` object. The last column is relative to that object.

| URL parameter | Stored as | Sent on order |
| --- | --- | --- |
| `utm_source` | `attribution.utm_source` | `utm_source` |
| `utm_medium` | `attribution.utm_medium` | `utm_medium` |
| `utm_campaign` | `attribution.utm_campaign` | `utm_campaign` |
| `utm_content` | `attribution.utm_content` | `utm_content` |
| `utm_term` | `attribution.utm_term` | `utm_term` |
| `gclid` | `attribution.gclid` | `gclid` |
| `aff` or `affid` | `attribution.affiliate` | `affiliate`; `affid` takes precedence |
| `sub1` to `sub5`, or `subaffiliate1` to `subaffiliate5` | Corresponding `attribution.subaffiliate1` to `attribution.subaffiliate5` | `subaffiliate1` to `subaffiliate5`; long names take precedence, values truncated to 225 characters |
| `fbclid` | `attribution.metadata.fbclid` | `metadata.fbclid` |
| `clickid` | `attribution.metadata.clickid` | `metadata.clickid` |
| `evclid` | `attribution.metadata.everflow_transaction_id` | `metadata.everflow_transaction_id` and root `everflow_transaction_id` |
| `funnel` | `attribution.funnel` | `funnel` |

Not supported on SDK 0.4.x: automatic attribution capture of `ttclid`, `msclkid`, `gbraid`, `wbraid` and `sg_evclid`. Keeping these values in the query string does not put them in order attribution. The live test confirmed that `ttclid` was absent from the SDK attribution.

Unconfirmed live: SDK 0.5.0 captures `ttclid`, `msclkid`, `gbraid` and `wbraid` in order `attribution.metadata`. Source confirms these additions; the live test used 0.4.43.

The cookies `_fbp` and `_fbc` map to `metadata.fb_fbp` and `metadata.fb_fbc`. On 0.4.43 the SDK reads them once per attribution collection, at SDK boot and again when the checkout form initializes. There is no delayed retry if the pixel sets them later. Missing cookies produce empty strings, which can overwrite earlier values. The SDK does not synthesize `_fbc` from `fbclid`.

Automatic metadata includes `landing_page`, `referrer`, `device`, `device_type`, `domain`, `timestamp`, `conversion_timestamp`, `sdk_version` and `user_ip`. The SDK also collects `fb_fbp`, `fb_fbc` and `fb_pixel_id`. In the live test, the order's `metadata.landing_page` was the checkout URL, not the first presell URL.

## How attribution persists

The last value per parameter wins. A tagged URL replaces the stored value for each parameter it contains; absent parameters keep their earlier values. Alias precedence still applies: a stored `affid` takes precedence over a later `aff`, and stored `subaffiliate1` to `subaffiliate5` take precedence over the corresponding short names.

SDK 0.4.43 keeps attribution in `sessionStorage` for the browser tab. It also stores `evclid` and the funnel name in `localStorage`. The live test observed the query string carried through checkout, upsell and receipt URLs.

For links to other domains, configure `window.nextConfig.utmTransfer`:

| Key | Behavior on SDK 0.4.43 |
| --- | --- |
| `enabled` | Must be `true` to run link parameter transfer |
| `applyToExternalLinks` | Set to `true` to include external links; defaults to `false` |
| `excludedDomains` | String array matched as substrings of external link URLs |
| `paramsToCopy` | String array of URL parameter names. Empty or absent copies all current URL parameters |
| `debug` | Enables extra logging |

The transfer snapshots the current URL parameters at boot and appends missing parameters when you click a link. It keeps values already present in the destination link.

Attribution is sent on prospect cart creation and order creation, including express payment orders. A failed prospect cart creation retry omits attribution. Upsell requests do not send it.

See [checkout-link parameters](/docs/storefront/checkout-links) for checkout links, and [marketing attribution](/docs/apps/guides/marketing-attribution) for reading attribution from the `order.created` webhook.

## Adding your own attribution values

Use these SDK 0.4.43 methods to inspect or add attribution before your order is created:

| Method | Behavior |
| --- | --- |
| `next.addMetadata(key, value)` | Merges one key into `attribution.metadata`; returns void |
| `next.setMetadata(metadata)` | Merges an object into existing metadata, without replacing it; returns void |
| `next.setAttribution(attribution: Record<string, any>)` | Shallow-merges top-level attribution fields and merges any supplied `metadata`; returns void |
| `next.getAttribution()` | Returns the order-API attribution shape |
| `next.debugAttribution()` | Prints attribution in a console group; returns void |

`setAttribution` does not update the separate stored URL-parameter copies. Collection on the next page can overwrite values you set with it.

For example, capture `ttclid` as custom metadata on SDK 0.4.x:

```javascript
window.nextReady = window.nextReady || [];
window.nextReady.push(function (next) {
  const ttclid = new URLSearchParams(window.location.search).get('ttclid');
  if (ttclid) {
    next.addMetadata('ttclid', ttclid);
  }
});
```

On Shop Sync stores, metadata keys reach Shopify only if you map them. See [tracking on Shop Sync stores](/docs/campaigns/tracking/shop-sync). Unconfirmed live: Shop Sync metadata delivery was source-checked but was not part of the live test.

## Where to read attribution

Read your order's `attribution` object in the Admin API or the [Campaigns API](/docs/campaigns/api). The live test checked the Admin API order and confirmed the UTM fields, `gclid`, `affiliate`, `subaffiliate1`, `funnel` and `metadata.fbclid`.

| Field in `attribution` | Contents |
| --- | --- |
| `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term` | Captured campaign parameters |
| `affiliate` | Affiliate value |
| `subaffiliate1` to `subaffiliate5` | Subaffiliate values |
| `gclid` | Google click ID |
| `funnel` | Funnel name |
| `everflow_transaction_id` | Captured `evclid` |
| `metadata` | Captured metadata and values you added |

The SDK sends non-empty top-level attribution fields and the metadata object. It does not send `first_visit_timestamp` or `current_visit_timestamp` to the API.

For order notifications, read attribution from the `order.created` [webhook](/docs/webhooks).
